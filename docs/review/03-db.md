## 1. Schema e flussi

Il database `%APPDATA%/Audit/audit.db` usa WAL, `synchronous = NORMAL`, foreign keys e `user_version = 1`.

Tabelle:

| Tabella | Uso reale |
|---|---|
| `tracks` | fonte autoritativa della libreria |
| `roots` | root scelte dall'utente |
| `downloads` | journal dei download, scritto ma mai letto per query |
| `playlists`, `playlist_tracks` | create, mai usate |
| `meta` | `scannedAt` |
| `tracks_fts` | ricerca full text, trigger insert/update/delete |

Flusso di scrittura:

1. `library:scan` produce JSON dal sidecar.
2. Il renderer chiama `library:saveCache` con tutte le tracce.
3. `saveLibraryCache` fa `upsertTracks`, `replaceRoots`, `setMeta`, poi riscrive il JSON di backup.
4. `recordDownload` aggiorna `downloads` e `tracks.downloaded_at`.

Il flusso e' coerente per l'import legacy, ma non ha una fase di prune e non ha un modello di "scansione completata".

## 2. Finding

### AUD-201 - Nessun prune: le tracce rimosse restano per sempre

- Severita': ARANCIONE
- Layer: DB
- Categoria: integrita' dati
- File: `src/main/library.ts:66-86`, `src/main/db.ts:190-219`
- Problema: `saveLibraryCache` fa solo upsert. Se un file viene cancellato, spostato o una root viene rimossa, la riga resta in `tracks`, compare nella ricerca, nelle tile, nei gruppi e nelle playlist per path. `downloads` resta orfano.
- Evidenza: non esiste `DELETE FROM tracks WHERE ...` in `db.ts`; `replaceRoots` sostituisce solo le root.
- Soluzione: usare una generazione di scansione (`meta.scanGeneration`) o una tabella temporanea delle tracce viste; al termine, in transazione, cancellare le tracce sotto le root scansionate che non sono state viste, con eccezione per file temporaneamente non leggibili. Prunare anche `downloads` e i path delle playlist.
- Alternative: soft delete con `missing_since` e una vista "available"; piu' sicuro per dischi rimovibili.
- Sforzo: M. Impatto: alto sulla correttezza percepita.

### AUD-202 - Il tag editor non aggiorna il DB e perde il genere inferito

- Severita': ARANCIONE
- Layer: DB / renderer / sidecar
- Categoria: integrita' dati, coerenza UI
- File: `src/main/ipc-handlers.ts:61-69`, `src/main/library.ts:173-221`, `python/library/scan.py:299-307`, `src/components/player/TagEditor.tsx:15-37`, `src/components/player/PlayerSection.tsx:345-349`
- Problema: `library:writeTags` scrive il file ma non fa upsert nel DB. Il renderer sostituisce la traccia con il risultato Python, che non contiene `genre_guess`, `genre_confidence`, `genre_source` ne' `genre_rule`. Dopo un riavvio il DB mostra i vecchi tag finche' non termina una nuova scansione; la chip del genere sparisce subito.
- Evidenza: `writeTrackTags` non chiama `upsertTracks`; `write_tags` restituisce `_read_tags(p)` senza `infer_tracks`; `handleTagSaved` rimpiazza l'oggetto con quello restituito.
- Soluzione: dopo una scrittura riuscita, eseguire l'inferenza del genere sulla traccia aggiornata e fare upsert in transazione con FTS. Restituire la traccia arricchita. Invalidare la cache art se il tag contiene nuova art.
- Alternative: rileggere la traccia con `library:scan` sul singolo file, piu' lento ma semplice.
- Sforzo: S. Impatto: alto su coerenza e persistenza.

### AUD-203 - Identita' del path non canonica; journal non transazionale

- Severita': GIALLO
- Layer: DB / main / sidecar
- Categoria: integrita' dati
- File: `src/main/db.ts:160-188`, `255-263`; `src/main/python-bridge.ts:210-228`; `python/downloader/core.py:542-545`
- Problema: la chiave primaria e' la stringa del path. Su Windows lo stesso file puo' arrivare con case, separatori o `..` diversi. `recordDownload` cerca `tracks.path` con uguaglianza esatta e puo' non aggiornare `downloaded_at`; il journal puo' contenere un path diverso da quello scansionato. Le due scritture di `recordDownload` non sono in transazione.
- Evidenza: `UPDATE tracks SET downloaded_at = ? WHERE path = ?`; `upsertTracks` usa il path cosi' com'e'; nessuna normalizzazione in `library.ts` o `scan.py`.
- Soluzione: colonna `path_key` canonica (lowercase su Windows, separatori `/`, `realpath` quando possibile) con indice unico; conservare `path` per la visualizzazione. Usare `path_key` per journal, playlist e update. Avvolgere journal e update in una transazione.
- Alternative: normalizzare solo al confine (`scan`, `result`, `saved`) e mantenere il resto invariato.
- Sforzo: M. Impatto: medio, ma evita duplicati e sort "recenti" incompleti.

### AUD-204 - FTS: input non valido e riscrittura eccessiva

- Severita': GIALLO
- Layer: DB / renderer
- Categoria: robustezza, performance
- File: `src/main/db.ts:109-130`, `279-301`; `src/components/player/LibraryHome.tsx:124-168`
- Problema: `ftsQuery` produce una stringa vuota o non valida per input di soli segni (per esempio `""` o `**`), e `queryTracks` non ha try/catch. La Promise viene rifiutata, `fetchPage` ha solo `try/finally` e non mostra errore. Inoltre il trigger `tracks_au` cancella e reinserisce la riga FTS a ogni upsert, anche se i campi non sono cambiati; una scansione completa riscrive tutte le righe.
- Evidenza: `tokens.map(...).join(' ')` puo' restituire `''`; `MATCH @fts` viene eseguito senza validazione. Il trigger e' `AFTER UPDATE`, non `AFTER UPDATE OF title, artist, album, genre, genre_guess`.
- Soluzione: sanitizzare i token (`[a-z0-9]`), scartare query vuote, usare `MATCH` solo se c'e' almeno un token, aggiungere un fallback `LIKE` e un `try/catch` con errore UI. Valutare FTS5 external content e trigger `UPDATE OF` per ridurre le scritture.
- Alternative: usare `LIKE` per la ricerca semplice e FTS solo per query lunghe.
- Sforzo: S. Impatto: medio.

### AUD-205 - Sort "downloaded" non usa l'indice; "added" e' un campo morto

- Severita': GIALLO
- Layer: DB
- Categoria: performance, correttezza
- File: `src/main/db.ts:77-78`, `270-277`, `74-75`
- Problema: l'indice e' su `downloaded_at DESC`, ma l'ORDER BY usa `COALESCE(t.downloaded_at, t.mtime) DESC`, quindi SQLite non puo' usarlo. `added_at` non viene mai popolato: il sort "added" equivale a `mtime` e non e' esposto nella UI.
- Evidenza: `ORDER_BY.downloaded` e `ORDER_BY.added` usano `COALESCE`; nessun `INSERT`/`UPDATE` scrive `added_at`; `LibraryHome` non offre "added".
- Soluzione: indice su espressione `COALESCE(downloaded_at, mtime) DESC` (SQLite supporta gli indici su espressione) oppure colonna materializzata `effective_sort_at` aggiornata su scan/journal. Rimuovere `added` dal tipo o popolarlo alla prima scansione.
- Alternative: paginare in memoria per 1.400 tracce; non scala.
- Sforzo: S. Impatto: basso oggi, medio oltre 10.000 tracce.

### AUD-206 - Migrazioni non transazionali, nessun backup, nessuna chiusura

- Severita': GIALLO
- Layer: DB
- Categoria: affidabilita'
- File: `src/main/db.ts:35-135`
- Problema: `migrate` esegue DDL con `database.exec` senza transazione esplicita e imposta `user_version` anche se una parte dello schema e' fallita. Non c'e' backup prima della migrazione, ne' `close()` su quit, ne' `integrity_check` dopo un crash.
- Evidenza: `database.exec(...)`; `database.pragma('user_version = ...')` fuori da una transazione; nessun hook di chiusura in `main.ts`.
- Soluzione: `database.transaction(() => { ... DDL ...; user_version = N })()`; backup del file prima di una migrazione; `closeDb()` su `will-quit` con checkpoint WAL; integrity check opzionale all'avvio.
- Alternative: usare un migration runner con file versionati e rollback.
- Sforzo: M. Impatto: medio, soprattutto con upgrade futuri.

### AUD-207 - Schema e API morti; backup JSON riscritto a ogni salvataggio

- Severita': VERDE
- Layer: DB
- Categoria: manutenzione
- File: `src/main/db.ts:91-102`, `265-268`; `src/main/library.ts:66-86`; `src/types/electron.d.ts:195-198`
- Problema: `playlists`, `playlist_tracks`, `getDownloadedAt`, `libraryStats` e `library:recordDownload` non sono usati dal renderer. `saveLibraryCache` riscrive l'intero JSON di backup a ogni scansione, in modo sincrono nel main.
- Evidenza: grep di `libraryStats`/`recordDownload` mostra solo main e tipi; nessun handler playlist; `fs.writeFileSync` del JSON.
- Soluzione: o completare le feature (playlist DB, statistiche UI), o rimuovere lo schema/API. Tenere il JSON solo per export/import manuale o migrazione.
- Alternative: lasciare il JSON come backup ma scriverlo in background e solo quando cambia.
- Sforzo: S. Impatto: basso.

## 3. Analisi query

- `listTracks()` carica tutte le righe e le mappa: viene usato all'avvio dal renderer, quindi il beneficio della paginazione e' parziale.
- `queryTracks` usa statement preparati e parametri nominati, con `ORDER BY` da mappa fissa: buono.
- Il conteggio `total` e la pagina sono due query separate: corretto per paginazione, ma senza transazione snapshot; con scan concorrente i due risultati possono differire.
- `libraryStats` calcola generi con subquery e `GROUP BY`: indicizzato solo su `genre_guess`, non su `COALESCE(genre_guess, genre)`.
- `recordDownload` non e' idempotente rispetto a path con case diverso; vedi `AUD-203`.

## 4. Punti di forza

- WAL e `synchronous = NORMAL` sono una scelta corretta per un'app desktop locale.
- `foreign_keys = ON`, transazioni per upsert e roots, statement preparati.
- Trigger FTS completi per insert/update/delete.
- Import legacy idempotente: `importLibraryCache` non fa nulla se `tracks` non e' vuota.
- `COALESCE` preserva `added_at` e `downloaded_at` quando una scansione non li fornisce.
- Tipi condivisi per query, stats e tracce.
- Journal best effort: un errore di journal non blocca il download.
